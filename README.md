# Etsy 运营任务管理系统（一期 + 二期）

对照截图复刻的多表任务管理系统，当前完成的能力：

**一期**
- 4 张业务表：SKU管理表 / AI主图二创任务表 / 套图任务表 / 待上架表（字段定义见 `app/schemas_config.py`，改字段不用改数据库）
- 记录的增/删/改/查
- 多视图（Grid 默认视图 + 可保存的自定义筛选/排序视图，对应截图里的 tab 切换）
- 筛选（按字段类型给出对应的操作符：包含/等于/大于小于/是否勾选等）与排序
- 账号登录注册 + 简单权限（第一个注册账号自动成为管理员；普通成员只能删除自己创建的记录，管理员可删除任意记录；每条记录自动记录"创建人""创建时间"）

**二期**（详见下方"二期：自动化规则"章节）
- 3 张配置表：任务负责人配置表 / 店铺配置表 / 品类负责人配置表
- SKU 创建自动生成 AI 主图任务、AI 任务完成自动生成套图任务、套图任务完成自动生成上架任务、上架状态自动同步回 SKU 开发阶段
- 任务负责人按配置表顺序轮询分配

**暂未包含**（留到三期）：
- 仪表盘统计页面
- 更复杂的权限（字段级/表级可见性控制）
- 附件上传（现在"成品附件"用链接代替）

## 部署到 Debian 服务器

### 1. 安装 Docker（服务器上执行，需要 root 或 sudo）

```bash
# 更新软件源
sudo apt update && sudo apt install -y ca-certificates curl gnupg

# 添加 Docker 官方源
sudo install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/debian/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg
sudo chmod a+r /etc/apt/keyrings/docker.gpg
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/debian \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin

# 验证
docker --version
docker compose version
```

### 2. 上传代码到服务器

在你本机把 `etsy-system` 整个文件夹打包，然后（任选一种方式）：

```bash
# 方式一：scp 直接传（在你本机执行）
scp -r etsy-system 用户名@服务器IP:/opt/

# 方式二：先在服务器建目录，再用 sftp / rsync 传
```

### 3. 配置环境变量并启动

```bash
cd /opt/etsy-system
cp .env.example .env
nano .env   # 把密码和密钥改成你自己的强随机值

docker compose up -d --build
docker compose ps        # 确认 web / db 两个容器都是 running / healthy
docker compose logs -f web   # 看启动日志，确认没有报错
```

启动后系统监听在服务器的 `8000` 端口。

### 4. 开放端口 / 配置反向代理（二选一）

**简单方式**：直接开放 8000 端口访问（测试阶段够用）
```bash
sudo ufw allow 8000/tcp
```
然后浏览器访问 `http://服务器IP:8000`。

**生产推荐方式**：用 Nginx 做反向代理 + 域名 + HTTPS（Let's Encrypt）
```bash
sudo apt install -y nginx certbot python3-certbot-nginx
```
新建 `/etc/nginx/sites-available/etsy-system`：
```nginx
server {
    listen 80;
    server_name your-domain.com;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```
```bash
sudo ln -s /etc/nginx/sites-available/etsy-system /etc/nginx/sites-enabled/
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d your-domain.com   # 自动签发并配置 HTTPS
```

### 5. 首次使用

访问站点 → `/register` 注册第一个账号（自动成为管理员）→ 之后同事注册的账号默认是普通成员。

## 二期：自动化规则（已完成）

新增 3 张配置表 + 4 条自动化规则，代码都在 `app/automation.py`，逻辑集中、方便你后续调整。

### 配置表怎么填

- **任务负责人配置表**：`任务类型` 选择"AI主图任务"/"套图任务"/"上架任务"其中一个，`负责人` 按顺序用英文逗号分隔填，比如 `邓诗雨,聂绎锦,王可丰`。系统每次自动创建该类任务时会按顺序轮流分配，`下一个轮到第几位` 会自动往后推进，一般不用手动改（除非想重置轮询顺序）。
- **品类负责人配置表**：`一级类目`/`二级类目` 分别填类目名称（跟 SKU 表"商品类目"字段里用的名字保持一致，比如"数字产品"），`负责人` 填对应的人名。
- **店铺配置表**：`店铺名`/`店铺备注`/`所属品类`，目前仅作资料维护，暂未接入自动分配逻辑（如果你希望改成按店铺分配店铺负责人，告诉我再加）。

### 自动化规则

1. **SKU 创建** → 自动生成一条「AI主图二创任务」（制作人按任务负责人配置表轮询分配），SKU「开发阶段」自动变为"AI主图制作中"。
2. **AI主图任务状态变化** → 实时同步 SKU「开发阶段」；变为"已完成"时自动生成「套图任务」（同一条 AI 任务只会触发一次，不会重复生成）。
3. **套图任务状态变化** → 实时同步 SKU「开发阶段」；变为"已完成"时自动生成「上架任务」——店铺负责人优先按 SKU 品类去品类负责人配置表匹配，匹配不到则走任务负责人配置表轮询兜底。
4. **上架任务"是否已上架"勾选/取消** → 实时同步 SKU「开发阶段」为"已上架"或"待上架"。

SKU 的「开发阶段」字段现在完全由系统自动维护，新建/编辑 SKU 时不会再出现这个字段的输入框。

## 五次补充调整（本轮更新 —— 稳定性 + 归档 + 视图增强）

### 🔧 稳定性修复（这是本轮最重要的部分）

排查后发现：之前的架构里，"保存一条记录"和"保存后触发的自动化联动"绑在同一个数据库事务里——只要联动逻辑（比如同步字段、自动生成下游任务）里有任何一点小问题，整个保存请求就会跟着失败，表现出来就是"改完东西之后，后面提交什么都报错"。这轮做了几处根本性加固：

1. **保存与自动化彻底解耦**：现在任何一次新增/编辑，先把这条记录本身安全提交，成功了才会再触发后续的自动化联动（生成下游任务、同步字段等），且每个自动化步骤都是独立的小事务。就算某个自动化环节出错，也只会跳过那一步、记一条日志，**不会导致你保存不了数据**。
2. **应用启动阶段也做了同样的加固**：以前如果某个启动时的数据迁移脚本报错，整个应用会直接起不来、容器不断重启（这很可能是这次"系统崩溃"的真正原因）。现在启动时的维护性步骤都单独兜底，一步出错不影响应用正常启动。
3. **查询接口兜底**：如果某条历史脏数据导致筛选/排序时类型转换出错，现在会自动降级成"不筛选不排序"的默认列表返回给你，而不是直接报错让你连数据都看不到。

**关于"重置系统"**：不需要，也不建议——重置会丢光数据。这轮改完之后，即使还有没发现的小 bug，也不会再让你没法正常使用系统。如果重新部署之后还遇到"请求失败"，麻烦把这条命令的输出发给我：
```bash
docker compose logs --tail=100 web
```
留意里面 `[automation]` 或 `[startup]` 开头的报错堆栈，那就是具体卡在哪一步了，我可以针对性地修。

## 六次补充调整（本轮更新 —— 多店铺按类目自动分配）

之前"店铺配置表"只是一张资料表，没有真正参与分配。这轮把它升级成实际生效的分配规则：

1. **店铺配置表新增"店铺负责人"字段**（从用户管理名单选），"所属品类"改成跟"品类负责人配置表"联动的多选（避免手打类目名跟别处对不上）。
2. **待上架表新增"所属店铺"字段**：套图任务完成自动创建上架任务时，会按 SKU 的品类去匹配店铺配置表——**匹配到哪个店铺，"店铺负责人"就是这个店铺的负责人，"所属店铺"也会一起自动填上**。
3. **三层兜底，不会出现分配不出人的情况**：
   - 第一优先：店铺配置表按品类匹配到店铺 → 用这个店铺的负责人；
   - 匹配不到店铺，但品类负责人配置表里有对应负责人 → 用这个（只有负责人，没有店铺名）；
   - 都匹配不到 → 退回任务负责人配置表轮询分配。

字段结构变化都不需要手动迁移，直接重启：


### 部署后建议检查

1. 管理员账号去"店铺配置表"，给每个店铺配好"所属品类"和"店铺负责人"。

## 十次修复 —— 真正找到"回弹到待制作"的原因了！

多亏你贴的日志，这次终于抓到真凶。日志里清清楚楚显示：

```
08:25:45  收到的字段={'status': '已完成'}   ← 保存成功
08:25:46  收到的字段={'status': '待制作'}   ← 一秒后又收到一次新请求，把它改回了待制作！
```

**不是自动化把值改回去的，是前端浏览器又发了一次新的保存请求**，带着旧值。根因是：点击单元格进入编辑状态时，代码会先异步刷新一次下拉选项（因为选项可能来自配置表），但"这个格子正在编辑中"这个防重复点击的标记，是在这次异步等待**之后**才打上的。如果用户连续点了两下同一个格子（比如手速快、或者网络慢导致第一次点击的异步操作还没返回），就会在这个等待间隙里并发触发出两个互相不知道对方存在的下拉框——用户实际操作、选了"已完成"的那个正确保存了，但另一个没人碰过、还停留在"待制作"这个初始值的"幽灵"下拉框，之后自己失焦触发保存，把刚保存对的值又覆盖回了旧值。

**修复方式**：把"正在编辑"这个标记提前到异步刷新选项之前就打上，从根上堵住这个并发窗口——现在连续点击同一个格子，第二次点击会被直接忽略，不会再产生"幽灵编辑会话"。
